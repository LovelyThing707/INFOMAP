Critical 自分で再現

買い手は「当たり／外れ」を一度も申告できない。返金経路が存在しない

submit_verdict の中の escrow = case when p_verdict = 'hit' then 'released' else 'refunded' end は、 両分岐が型のないリテラルなので Postgres が式全体を text と解決する。 enum 列への代入に text→enum の経路は無く、hit でも miss でも必ず例外で落ちる。 最小再現も、全 migration を当てた実スキーマでの再現も一致した。

影響が大きいのは、失敗が誰にも見えないこと。クライアントは rpcVoid 経由で呼んでおり、 この関数は Supabase のエラーを一切読まない（コメントは「黙って捨てず」と書いてあるが、実装は捨てている）。 画面は何事もなかったように振る舞う。

連鎖して壊れるものが重い。hit_count / miss_count / gone_count / restricted_until を書き換えるコードは この関数の中にしか存在しない。 つまり本番では売り手スコアが永久に null、悪質出品者の出品制限も永久に発火しない。 そして run_tick は2時間後に全ての held を無条件で released にするので、 買った情報が嘘でも金は必ず売り手に渡る。

クライアント構想の7ステップとの照合

構想の各段を、実際の画面・RPC・DB で辿った結果。

  1. 品Aを買いたい成立

    地図と検索で探せる。既定は「募集」モード。

  2. 近くの店を回るが売り切れアプリ外

    —

  3. どこにあるか分からない導線が切れる

    販売モードで空振りしたとき、依頼へ誘導するボタンが無い。空の状態は文言だけで、検索語も依頼作成画面に引き継がれない。ここは数行で直せるが、体験の要。

  4. 有料で情報提供を募る本番で不可

    フォーム自体はよく出来ている（範囲・報酬・採用人数・締切・「無かった場合も払うか」まで先回りして聞く）。だが送信には残高が要り、入金手段が無いため本番では1件も作れない。

  5. 集まる届かない

    集まるのは「情報の提案」ではなく「向かう」という宣言。依頼の寿命は30〜120分だが、プッシュ通知も Realtime も依存に入っていないので、アプリを開いていない供給者には事実上届かない。

  6. 実績をもとに信頼度を判断して買う未実装

    構想の中核だが、依頼フローには「買う前に選ぶ」構造が無い。応募者が報告本文と写真を先に渡し、依頼者は全文を読んでから採用/不採用を押す。応募者一覧には絵文字と名前しか出ない。詳細は次節。

  7. 行って買えた記録されない

    結果の申告はピン購入にしか無く、依頼の報告が正しかったかは記録されない。だから実績も積み上がらない。

販売（ピン）側の「情報を買う前に中身が見えない」問題への回答は筋が通っている。 未購入者向けの型 PublicPin は本文フィールドを構造として持たず、DB でもビュー越しにしか渡さない。 買う前には「撮影の裏づけ」（対象から何m・何分前・測位誤差・偽装申告の有無）だけを見せる。 これはマスクではなく不在なので、実装として強い。ただしその信号が一覧・地図には出ず、詳細を開くまで届かないため、 「複数集めて実績で選ぶ」という比較の場では機能していない。

「実績で信頼を判断する」が成立しない4つの理由

構想の第6ステップは、この事業の差別化そのもの。現状は最も薄い。

1. 本番ではスコアが永久に null

前述のとおり実績カウンタを更新する唯一の関数が起動しない。加えて懸賞の採用（accept_bounty_application）は プロフィールのカウンタに一切触れないので、報告専業のユーザーは仕組み上ずっと「実績なし」。 代替指標の acceptedReportCount は Supabase 実装で 0 固定を返している。

2. 指標が1変数で、統計的に意味を持たない

スコアは hit / (hit + miss) のみ。時間減衰も、カテゴリ別も、件数の信頼区間も、買い手側の評価も無い。 表示は1勝0敗を「100%・緑」として熟練者と並べる。皮肉なことに、削除済みの旧実装には 「判定4件未満は非表示」という最小標本ゲートがあったが、撤去時に一緒に失われている。

3. 買い手側が無コストで踏み倒せる

miss の申告に証拠も担保も要らず全額返金される。しかも購入済みビューは escrow 状態を条件にしないため、 返金後も本文と写真を読み続けられる。「買う → 読む → 違っていたと申告 → 全額返金 → 情報は保持」がコスト0で回る。 買い手側には実績列そのものが無いので、虚偽申告の履歴も残らない。停止を負うのは売り手だけ。 （現時点ではこの経路自体が型エラーで動かないため実害は出ていないが、1行修正した瞬間に開く穴である。）

4. シビル耐性が無い

メール確認が無効で、誰でもアカウントを発行できる。共謀2アカウントで出品→購入→hit を回せば、 手数料20%だけを払って緑バッジを製造できる（¥100の情報なら実質¥20/件）。 逆に4アカウントの無料 miss 申告で、競合を24時間の出品停止に追い込める。 通報も3人で自動的にピンを取り下げるが、運営の判断が一切介在しない。フォロワー数も自己 insert で偽造できる。

ここが最大の投資判断ポイント。「情報の深度の差を金で買う」という構想の価値は、 売り手の信頼を買い手が事前に見積もれることに全面的に依存している。 現状はその機構が本番で1件もデータを蓄積しない。直すべき優先度は決済より上だと考える。

金アービトラージ・不動産予測への距離

この構想については、リポジトリ自身が既に一度答えを出している。

重要な発見がある。migration 20260831060000_tips.sql は、 非地理・非写真の「予想」商品（競馬の買い目）を完全に実装している。 そして同じコミットの中の 20260831070000_drop_tips.sql が、 そのテーブルと RPC を全て削除し、エスクローを返金して撤退している。

撤退の理由は実装を読めば分かる。予想商品では結果判定が売り手の自己申告にならざるを得ず、真偽検証が構造的に破綻する。 現在も catalog.ts は「見た事実ではない予想」を明示的な禁止事項として掲げている。 つまりクライアントが究極形として挙げた方向は、この開発者が一度試して意図的に捨てた道である。 これは失点ではなく、判断の記録として評価すべき点だと思う。

アービトラージ用途そのものの難点

  • 自己破壊性。先着枠は最大3、上限¥2,000。同じ裁定機会を複数人が買った時点で機会は消える。情報の価値と販売可能部数が反比例する。
  • 踏み倒しが常態化する。検証不能な相場情報では、読んだあと too_thin で全額返金する動機が常に勝つ。
  • 語彙が全て現地前提。外れ理由は「着いたら売り切れ」「写真が別の場所」「内容が薄い」の3種のみ。
  • 法的性質が変わる。不動産の値上げ予測は投資助言（金商法）や媒介性（宅建業法）に触れうる領域で、店舗の仕入値は不正競争防止法の営業秘密に関わる。※法務確認が必要な論点として提示するもので、私は法律家ではない。

提案。この方向は「将来のビジョン」として資料に置くのは有効だが、 PMF 検証の対象からは外すべき。まず単価を上げられる現地確認（法人の店頭調査・什器や棚割の確認・物件の現況確認）で ¥2,000 の上限を外すほうが、同じ構造のまま経済性が改善する。

決済と法規制

未着手であること自体は正しい判断。ただし着手順序を間違えると作り直しになる。

台帳の設計は良い。残高カラムを持たず、available と pending の増減を1行に両方持たせることで、 「預かりへ移す」が1行で表現され片側だけ更新される事故が起きない。問題は台帳の外側にある。

資金決済法上の類型が未決定

現行の残高は3類型のどれとも整合しない中間状態にある。チャージして買うなら前払式支払手段だが、 出金機能があるため「払戻し可能＝前払式ではない」側に倒れる。A の入金が B の出金として出るなら為替取引で資金移動業。 売買代金を預かって売り手へ渡すだけなら収納代行だが、2021年改正で「個人が受取人となる収納代行」は原則として資金移動業に取り込まれた。 本サービスの受取人はまさに個人（売り手・報告者）である。

実装への影響が決定的なので順序が重要。収納代行に寄せるなら残高の滞留と出金機能を捨てて都度決済＋PSP経由送金にする必要があり、 ledger.ts の hold/settle モデルごと書き直しになる。類型を法務と確定する前にコードを書き始めてはいけない。

見落とされている悪用シナリオ

  • 懸賞による代理ストーキング。依頼の座標は自由入力で、サーバー側にエリア検証が無い。 「この座標の家に車があるか、写真つきで」は現行コードで完全に成立する。禁止事項の第1項がまさにこれを禁じているのに、最も検知不能。
  • 報告者の物理的安全。依頼者は応募者が特定の座標へ30分以内に来ることを事前に知れる（heading 状態と距離）。待ち伏せの下地になる。緊急連絡も安全ガイドも無い。
  • 転売助長。唯一の有効カテゴリが店頭在庫で、例文は品薄ゲーム機。買いたい消費者と転売目的をコード上で区別する仕組みが無い。決済代行の加盟店審査とストア審査の両方で落ちやすい典型。
  • 店舗規約違反の教唆。店内撮影は多くの小売で禁止されている。撮影証拠を必須にする設計は、構造的にそれを勧めている。店舗からのオプトアウト窓口が無い。
  • 自己取引による資金洗浄。KYC もシビル耐性も無いので、入金→別アカウントで自分の情報を買う→出金、で20%だけ払って出所を洗える。

ユニットエコノミクス

ここが一番早く効いてくる制約だと思う。

価格域 ¥50–2,000、手数料 floor(amount × 0.2)。つまり1取引あたりの粗利は ¥10〜400、 中央価格帯なら ¥40〜100。ここから決済手数料（Stripe なら 3.6%＋固定、IAP 判定なら 15〜30%）と 振込手数料 ¥150〜250/件 が引かれる。最低出金額の定義がコードに無いので、 現状は ¥40 の出金申請が通る設計で、1件ごとに赤字になる。

供給側の労働経済が先に破綻する。¥100〜500 の報酬のために現地へ移動して撮影する労働は、移動込みで15〜30分。 時給換算 ¥200〜1,000 で、東京都の最低賃金を下回る。 需要仮説を検証する前に、供給側が経済的に成立するかを先に検算すべき。 これは価格上限を上げるか、1回の移動で複数の依頼をまとめて処理できる設計にするかでしか解けない。

Apple / Google の課金規約

売っているのは「アプリ内でアンロックされるテキストと写真」で、デジタルコンテンツの典型形に見える。 IAP 必須と判定されれば 15〜30% が上乗せされ、自社の 20% と合わせて粗利が消える。 「実物のモノ・サービスの手配」例外に当たるかは非自明。 これは法務より先に、Apple の事前レビュー相談で確定させるべき唯一の問いで、 答え次第で「出品の主戦場はネイティブ」という前提もアーキテクチャも調達ストーリーも変わる。
